# Repository and build design

## Proposed repository layout

```text
.
├── .copr/
│   └── Makefile
├── .github/workflows/          # or equivalent on the selected forge
├── docs/
├── packages/
│   ├── aquamarine/
│   │   ├── aquamarine.spec
│   │   ├── sources             # checksums or source metadata
│   │   ├── patches/
│   │   └── README.md           # provenance and package-specific notes
│   └── ...
├── scripts/
│   ├── build-local
│   ├── check
│   ├── render-build-order
│   └── release
├── package-set.yaml            # versions, upstreams, tiers, and dependencies
├── LICENSE
└── README.md
```

All generated files must be reproducible from tracked inputs. Do not commit
COPR tokens, forge tokens, downloaded source archives, RPMs, SRPMs, Mock roots,
or build logs.

## Source flow

```text
upstream signed/tagged release
          |
          v
package-set.yaml + spec + patches + checksums
          |
          v
make srpm downloads/checks sources and creates an SRPM
in COPR's source-build environment
          |
          v
Mock builds binary RPMs with build-network access disabled
          |
          v
development repository -> gates -> atomic metadata regeneration
```

Use release archives pinned to an immutable tag or commit. Record the upstream
URL, version, archive checksum, license, and any patch origin in each package's
README. Rust, Go, or other ecosystems that normally fetch dependencies must use
a prepared vendor archive or Fedora's approved vendoring workflow.

## COPR integration

Define each source package in COPR as an SCM package:

- clone URL: this repository's public HTTPS URL;
- subdirectory: `packages/<source-package>`;
- spec: `<source-package>.spec`;
- source-build method: `make_srpm` using the tracked `.copr/Makefile`;
- auto-rebuild: off for production.

The `rpkg` method was considered first, but rpkg-util v3 requires source files
to be present or generated by an rpkg template. This packaging monorepo neither
commits upstream archives nor contains upstream worktrees to pack. COPR's
documented `make_srpm` method instead lets the source-build stage fetch the
ordinary spec's `Source0`, verify it against the tracked SHA-256, and emit the
SRPM. Network access remains disabled for the later binary Mock build.

Automatic rebuilds on every push are unsafe for an ordered ABI stack. A release
script should submit build batches in dependency order. COPR makes successful
development-repository results available to later builds, so dependent waves
can build before public metadata is regenerated.

Pull requests may use COPR subprojects such as
`hyprland:pr:<number>`. They remain isolated from production while inheriting
the main project repository as a build source.

## Package manifest

`package-set.yaml` is the source of truth. Its minimum schema is:

```yaml
schema: 1
release_set: "YYYY-MM-DD.1"
packages:
  hyprutils:
    upstream: https://github.com/hyprwm/hyprutils
    version: "<stable-tag-version>"
    source_sha256: "<sha256>"
    tier: core
    depends_on: []
  hyprland:
    upstream: https://github.com/hyprwm/Hyprland
    version: "<stable-tag-version>"
    source_sha256: "<sha256>"
    tier: core
    depends_on:
      - aquamarine
      - hyprgraphics
      - hyprlang
      - hyprutils
```

The implementation should validate names, unique versions, checksums, known
tiers, dependency existence, and an acyclic graph. Build order must be derived
from this graph and checked against spec-file BuildRequires.

## Versioning policy

- Use upstream stable versions as RPM `Version`, transformed only as Fedora's
  versioning rules require.
- Start a new package at `Release: 1%{?dist}`.
- Increment `Release` for packaging-only changes and reset it for an upstream
  version update.
- Do not publish the same Version-Release as Fedora. If a same-version rebuild
  is unavoidable, choose and document a release value that sorts newer on every
  target; verify it with `rpmdev-vercmp` before building.
- Avoid `Epoch`. Preserve an existing Fedora epoch, and add a new one only after
  documenting why version comparison cannot otherwise be repaired.
- Plugins must encode a strict compatibility relationship with the Hyprland
  version or ABI they were built against.

## Quality gates

### Static and source gates

- spec parses on each supported Fedora release;
- sources are HTTPS, immutable, checksummed, and redistributable;
- `rpmlint` findings are reviewed, with exceptions recorded;
- patches carry an upstream issue/commit URL or a written Fedora-specific
  rationale;
- no network fetch occurs in `%prep`, `%build`, `%install`, or `%check`;
- no unowned directories, unexpected bundled libraries, or undeclared licenses.

### Build and repository gates

- clean Mock build for a representative stable chroot before COPR submission;
- COPR success for every required chroot/architecture;
- repository closure/repoclosure succeeds;
- clean-install and upgrade transactions succeed in disposable install roots;
- resulting RPM file lists and automatic Provides/Requires are reviewed;
- `Hyprland --version` and each installed first-party command start far enough
  to report a version/help result;
- plugin loading is tested with the matching Hyprland build;
- a nested or VM Hyprland session smoke test passes on `x86_64`; `aarch64`
  receives at minimum install and command-level smoke tests until hardware CI is
  available.

## Security and credentials

- COPR credentials live in `~/.config/copr` for local operation and in masked,
  protected CI secrets for automation.
- CI triggered by untrusted pull requests never receives production secrets.
- Release jobs are manual/protected and run only from the protected default
  branch.
- The build environment has no network unless source preparation for a specific
  package has a reviewed, temporary exception.
- Release archives and vendored dependency archives are checksum-verified.

## Observability

Every release records:

- release-set identifier and Git commit;
- upstream versions and checksums;
- COPR build IDs by package and chroot;
- failed/waived gates;
- publication time;
- rollback target (the prior known-good release set).

Keep that data in a tracked `releases/<release-set>.yaml` file once
implementation begins.
